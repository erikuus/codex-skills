# Swedbank Pay on VAU staging

Use this guide for the payment portion of a Swedbank Pay test. Read [the shared setup](shared.md) and the relevant order or enquiry guide for submission, staff processing, billing and post-payment checks. Those five guides record the EveryPay baseline. This guide records Swedbank Pay evidence separately. Use the provider and outcomes requested for the run. The current Swedbank Pay acceptance run uses Visa and bank payments while the Mastercard sandbox issue is open.

## Start a payment

1. Check that VAU points to staging, the provider uses its sandbox and ERPLY is the test account. Open the correct payable record and check the amount and account role. If the run needs callback or receipt attribution, use the `vau-test-logs` skill to take a baseline of `payment_trace.log` and applicable error logs. Record the case and available IDs before submitting.
2. In the webshop, the enabled Swedbank Pay component showed one VAU **Maksa** button. Click it once and follow the freshly generated hosted checkout. Verify the case and amount there. For an invoice or enquiry, check the actual payment entry point and follow the workflow's issued bill or notice. The webshop button only establishes the observed entry point for the shop.
3. In the hosted menu, use **Kaardimakse** for a supported sandbox card fixture, or **Maksa panga kaudu** for a bank. Use the current provider test instructions and the skill's credential/authentication handoff. Check the requested method and outcome before submitting. Use the [browser recovery procedure](../SKILL.md#recover-interrupted-browser-control) if the form stalls, a dialog blocks the view or a transition interrupts control.
4. For a bank case, select the requested offered bank and use its sandbox simulator. The webshop run observed **SETTLED** across the tested banks and **EXECUTED** settling for Coop. Record the applied simulator state and any notification indication, then use **Tagasi kaupmehe juurde** when the case calls for a browser return. Verify the resulting payment. A simulator label or “Notification sent” alone does not establish settlement or receipt creation.

For a normal return, follow the provider's return control once if shown. VAU can show a confirmation-in-progress page while callback, capture or accounting work completes. Wait within the case's observation window and inspect the same record before any retry. For a webhook-only case, leave the merchant return unused until the outcome has been verified independently. If the browser returns automatically, record that fact and use the trace to identify which request completed the payment. A webhook winning a race with the browser and a payment completing without a merchant browser return are separate cases.

## Verify the result

- **Provider.** Check the matching bound payment for the expected amount and instrument using the available provider evidence. A successful card payment needs a verified capture. A successful bank payment needs verified BankLink Sale evidence and should have no card capture request. `Initialized` with a failed attempt can still be retryable. Check whether the order or just that attempt failed before deciding what happens next.
- **VAU and trace.** Match the payment and request IDs and the provider order/reference. Follow `source=webhook` or `source=browser_return` and its UID from verification through the committed payment latch and corresponding ERPLY registration events. The request that sends the card capture can differ from the one that validates payment and registers the ERPLY receipt. In the webshop run, a later callback or browser worker could log that the payment was already validated. A pending/status page or HTTP 200 callback acknowledgment alone does not establish business completion.
- **Business result.** Verify the paid state, history and release or fulfilment behavior required by the workflow guide. Staging mail debug evidence can show the intended message and recipient. Test mailbox delivery separately if it is in scope.
- **ERPLY.** Apply the [shared Laekumised check](shared.md#erply-receipt-checks-for-all-workflows). Match one receipt to the ERPLY order/document, date, amount and method where the workflow has an ERPLY document. The expected payment types are `CREDITCARD` and `BANKLINK`. For a failed, canceled or pending case, verify that the case remains unpaid and compare against the receipt baseline. Pre-existing sales documents are expected in some workflows. If an accepted payment lacks its expected receipt, check saved records and trace evidence before any recovery action.
- **Recording.** Keep sanitized timestamps with timezone, case/payment/request IDs, provider order/reference, matching log UIDs, VAU result and ERPLY document/receipt. Note whether the browser returned, which request acquired the latch and which request registered the receipt. Include missing evidence and sampled-log limits. Keep credentials, full card data, cookies and session URLs out of the notes.
