# Technical writing

Identify the reader and what they need to do or understand. Read the existing document, its linked source of truth and an actual caller before changing wording. Preserve the author's scope, terminology, language and useful structure.

Choose the form by the reader's task. In a tutorial, guide a newcomer to a visible result. In a how-to, give an experienced reader the prerequisites, actions and success check for one job. In reference, organize exact names, inputs, defaults and behavior for lookup. In an explanation, connect a design choice to the constraint it resolves. A README can serve several purposes through clearly named sections.

For a proposed API or shared component, write a short usage example from the consumer's perspective first. Walk through the caller's setup, action, result and likely failure. Mark proposed interfaces as proposed. For a shipped interface check flags, defaults and paths against code and run representative examples where practical. Treat commands with external effects as examples unless their execution is in scope.

Edit for specificity. Replace vague claims with a concrete result, name the actor, and keep uncertainty supported by the record. Preserve code identifiers and repo formatting. Match the document's language; when Estonian language editing is requested, use the available Estonian editing guidance. Return the requested artifact and identify any example that could only be checked against source.
